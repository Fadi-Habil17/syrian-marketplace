# Frontend API issues

Checked against the canonical OpenAPI and current NestJS implementation. These issues do not require any changes to the frontend's outbound contract.

| Flow                                | Contract or implementation gap                                                                                                                                                                                                            | Web behavior                                                                                                                                                                                                 |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Delivery changes                    | `approveDeliveryTerms` needs a revision ID. `getDelivery` returns only the applied version number and neither lists pending revisions nor returns their amount and promised date. The notification DTO has only category and resource ID. | The seller can propose a change. Buyer self-service approval is unavailable until the buyer can read the exact revision before consenting.                                                                   |
| Admin users and drivers             | The admin mutations accept user, restriction and driver profile IDs. There is no admin account search, restriction directory or eligible-driver search API.                                                                               | Admins can perform the contracted actions using a known ID. Driver zone and moderation lists display their available resource IDs. Non-case delivery lookup is subject to backend delivery read permissions. |
| Professional directory and contacts | Public profile lookup is by ID. The catalog can find published service packages and load the owning profile. There is no standalone public professional profile search, and the public DTO does not project a phone or WhatsApp field.    | The directory lists published packages and exposes in-platform booking and inspection quotes. Professionals without a published package and off-platform contact links are unavailable in the web directory. |
| Figma store pickup                  | The store designs include personal pickup. OpenAPI `DeliveryMethod` contains only `SELLER` and `PLATFORM_DRIVER`.                                                                                                                         | Checkout offers the two contracted delivery methods.                                                                                                                                                         |
| Client review ownership             | A review DTO has no buyer ID or edit capability flag, and there is no own-review lookup. Eligible completed orders can create a review. The public seller review list is the available source for an existing review by order ID.         | The buyer sees the existing review when it can be found and can submit an edit under backend enforcement. Older reviews outside the fetched page may require the API to reject a duplicate create.           |
| Web notification scope              | The browser's one-use ticket is issued only for a named order. There is no web inbox-only ticket. Notification references have no explicit target type.                                                                                   | Order pages subscribe to live events and re-fetch authorization-filtered REST data. The inbox reads durable notices and polls while visible. Unknown notification categories link to the order list.         |
| Agreement preview                   | An order in negotiation can expose proposed scope and due date, but the canonical Order DTO does not expose a pending agreement object with its author or a version separate from the order version.                                      | The agreement action uses the current version and visibly prefills the backend's projected scope and due date. The API remains authoritative about the proposal the actor can confirm.                       |

See [OpenAPI](api/openapi.yaml) and [WebSocket events](api/WEBSOCKET_EVENTS.md).
