# Implement maps for the Syrian Marketplace

Implement the approved map feature end to end in this repository. Give buyers an optional private destination pin for store deliveries and professional visits. Add local discovery for stores and professionals who serve the selected location. Deliver both workflows on the responsive Next.js web app and the Expo apps for iOS and Android in Arabic RTL and English LTR.

## Repository rules

- Read [`AGENTS.md`](../AGENTS.md) and the approved [`MAP_FEATURE_REQUIREMENTS.md`](MAP_FEATURE_REQUIREMENTS.md). Review `MARKETPLACE_REQUIREMENTS.md` revision 1.2, `B4F_HACKATHON_RULES.pdf`, `docs/REQUIREMENTS_CHECKLIST.md`, `docs/BUSINESS_RULES.md`, `docs/ORDER_STATE_MACHINES.md`, `docs/PERMISSIONS_MATRIX.md`, `docs/API_CONVENTIONS.md`, and `docs/DEPENDENCY_SECURITY.md` before implementation. Inspect the current routes, client screens, and tests before choosing where to extend them.
- Keep the existing NestJS 10, strict TypeScript, PostgreSQL, Prisma, Next.js 15, React 19, and Expo stack. Reuse the modules that own addresses, catalog, service coverage, booking, checkout, and delivery. Cross module boundaries through exported application interfaces. Use the existing server-only typed API client for web and the shared REST contracts for mobile.
- Keep the Syrian geographic hierarchy authoritative for service coverage. Delivery fees come from the server's rules for the selected city, delivery method, and currency. Maintain both seller delivery and platform-driver delivery. Preserve all existing booking, payment, inventory, escrow, proof-of-delivery, and order transition rules. Limit GPS use to the two one-time buyer actions described below.

## 1. Add an optional private destination pin

- Extend the existing address create and edit screens. Retain the city, applicable area, and written address fields. Let the buyer place, move, or remove a pin manually. Start the map at the selected city or area when geographic center data is available.
- Add a **Use my location** button. Request foreground location permission only when the buyer presses it. Read the device location once and let the buyer adjust the pin before saving. Keep manual placement available if permission is denied, location is unavailable, or the request times out. If the map fails, let the buyer save or use the written address and complete the workflow. Preserve an existing pin during an address edit unless the buyer explicitly changes or removes it.
- Make the saved address selectable with or without a pin in store checkout, fixed-price professional booking, and professional inspection or quote requests. Snapshot the pin alongside the existing address at store checkout preview or service request creation. Later edits to a saved address apply to future uses. Render older address and order records without pin data as text-only addresses.
- Add an optional `pin` to the address contract. A set value is `{ latitude, longitude }`. For updates, omission preserves the saved value and `null` removes it. Validate finite numeric latitude and longitude in `[-90, 90]` and `[-180, 180]`, respectively. Enforce both ranges and the complete-pair-or-null constraint in PostgreSQL with a reviewed forward migration.
- Extend `listAddresses`, `createAddress`, and `updateAddress`, plus authorized order and delivery responses. The buyer can see their own pin. Sellers and professionals can see the order pin within their existing fulfillment access. Drivers can see it only during an active assignment, and admins can see it within their assigned case and its permissions. Reauthorize every read. On assignment end or replacement, deny subsequent reads and clear the previous driver's on-screen pin on update or refetch. Keep unassigned job offers at city or area granularity.
- Render the private pin as a client-side layer. Map-provider requests are for the visible map tiles. Keep exact pins, written addresses, account and order identifiers, and credentials out of provider URLs and referrers. The requested tiles can reveal the viewport. Keep private coordinates out of logs, analytics, shared caches, and realtime payloads. Use existing realtime signals to trigger an authorized refetch when appropriate.

## 2. Add public locations and local discovery

- Add a local discovery view with a map and a browsable list. Use the same paginated result set for both. A marker or list card opens the existing store or professional detail page. Cluster overlapping markers and keep their entries reachable through the list. Keep the list usable during map outages and when a result lacks a mappable point.
- Require a city and allow a valid area within that city. Include only eligible published businesses with active accounts. For a city-only search, include businesses with city-wide coverage. For a city-and-area search, include businesses that cover the full city or that specific area. Apply the same server-owned coverage policy used by the relevant marketplace flows. Recheck actual order eligibility through checkout or booking.
- Start search from the selected location. Add an optional **Near me** action that requests foreground permission when pressed and reads device location once. Round latitude and longitude to two decimal places on the client before sending the origin to the marketplace API. Use it for distance ranking while retaining the selected city or area as the coverage filter. On denial, timeout, or location failure, continue using the selected location. Keep the discovery origin in screen memory and exclude it from account records, persistent client state, logs, and analytics.
- Use approved city or area centers as approximate public locations. Label approximate points in both languages. Keep home-based activities at approximate locations. Allow an authorized store owner or professional to opt in to publishing an exact pin for a venue that receives customers. Require explicit confirmation that the point will be public. Allow withdrawal and return to approximate display on subsequent reads. Use a dedicated public location field or DTO projection populated from a reviewed geographic center or an independently provided public venue pin.
- Add optional centers to `City` and `Area` using a reviewed dataset with a documented source and license. Store public venue details with `Storefront` or the professional profile, including the explicit publication choice. Reuse the existing owner edit flows and enforce ownership and publication eligibility on the server.
- Use straight-line distance from the selected area or city center, or from the rounded **Near me** origin, to the public display point. Sort by distance with a stable result ID tie-breaker. Place results without a mappable point at the end. Support an optional business-type filter.
- Start the contract design with `POST /api/v1/discovery/local/search`, a read-only operation accepting `cityId`, optional `areaId`, `kind`, `origin`, `limit`, and `cursor`. `kind` accepts `STORE` or `PROFESSIONAL` and defaults to both. Return `{ items, nextCursor }` with each item's ID, kind, display name, region, optional public point and precision (`APPROXIMATE` or `PUBLIC_VENUE` when a point exists), and the identifier needed to open the detail page. Follow existing error and pagination conventions. Bind signed cursors to the search criteria through a digest that keeps coordinates out of the cursor payload. Apply private or no-store caching as appropriate to location-sensitive responses.

## 3. Validate the free map provider

- Use a provider with zero map-service operating cost for the initial release. Evaluate OpenFreeMap's OpenStreetMap-based vector tiles with the `Liberty` style, MapLibre GL JS for web, and MapLibre React Native for iOS and Android. Make the style URL configurable and show the required attribution. Verify usage and privacy terms before enabling the provider.
- Test availability on a user connection inside Syria. Sample all 14 governorates, including urban and rural locations. Verify that tiles and labels render, Arabic and English names are usable, pin placement works, and the list and written-address flows continue through tile failure.
- Verify dependency compatibility with the repository's Expo 54 and React Native 0.81 setup. MapLibre React Native requires a native app build separate from Expo Go. Document verified iOS and Android build and review-distribution steps, plus any actual configuration requirements. Continue provider-independent implementation if live in-country or native verification is unavailable, and record that verification as pending before provider approval.

## Acceptance scenarios

| Scenario | Expected result |
| --- | --- |
| Create, set, edit, and clear an optional address pin | Valid pairs save, an omitted update preserves the pin, explicit `null` clears it, and malformed, partial, or out-of-range coordinates fail at the relevant API and database boundaries. Legacy records render with their written address. |
| Store checkout, fixed-price booking, and inspection requests | Each accepts an eligible address with or without a pin. Changing the saved address after the snapshot leaves the order destination intact. Server coverage, fee, and payment checks continue to apply. |
| Permission denial, location timeout, and tile outage | Permission is requested on button press. Manual placement works when location is unavailable. During a tile outage the written-address workflow and discovery list still work. An existing pin survives a text-only edit. |
| Search by city, area, and **Near me** | Only businesses with matching coverage appear. List entries and map markers refer to the same results, with list access for entries that lack a marker. Test ordering, ties, cursor continuity, and invalid city/area pairs. The rounded origin affects ranking without being saved. |
| Publish or withdraw a venue point | An authorized owner can publish a public venue after confirmation and withdraw it. Subsequent reads return approximate coordinates after withdrawal. Home-based entries use approved geographic centers. |
| Protect the private destination | Unrelated accounts, unassigned or former drivers, and admins outside the case cannot access the pin. Reassignment updates access and clears the previous driver's displayed pin. Public responses, logs, event payloads, and analytics contain no private coordinates. |
| Verify platform and locale parity | Both workflows work in Arabic RTL and English LTR across responsive web, iOS, and Android. Confirm accessible list and address input paths and test real-device permission behavior. |
